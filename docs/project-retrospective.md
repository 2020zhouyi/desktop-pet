# 剑三小桌宠双项目复盘

日期：2026-07-13

本文复盘同一产品线下的两个独立子项目：

- `desktop-pet-mvp`：Electron 桌宠应用，是角色资源、运行行为和发布包的事实源。
- `desktop-pet-site`：Vite 展示站，是角色浏览、角色包下载和桌宠下载入口。

这两个目录是独立 Git 仓库。它们共享产品和资源契约，但不共享运行时、构建产物或提交历史。

## 一、最终形成的产品

### 桌宠应用

桌宠当前已经从早期的多功能原型收缩为一个边界清楚的桌面产品：

- 透明、无边框、始终置顶的 `PetWindow`；
- 只负责搜索、预览和确认选宠的 `ControlWindow`；
- 点击、横向拖拽、右下角缩放和四类气泡反馈；
- 当前角色、角色大小和开机自启的本地持久化；
- macOS Apple Silicon DMG 与 Windows x64 便携 ZIP；
- 25 个离线内置角色，以及用户可直接管理的统一宠物目录。

产品最重要的一次取舍不是继续增加功能，而是删除 settings、提醒、外部服务、复杂资源 CRUD 和主动行为等旁支，让桌宠回到“常驻、可玩、可换、可扩展”的核心体验。

### 展示站

站点最终不是桌宠的 Web 版本，而是一个轻量分发入口：

- 首页角色轮播和角色图鉴；
- 全部、门派、玩家、首领分类；
- 桌面、平板、手机分别以 10、8、4 个角色分页；
- 每个角色展示待机动画，并提供可导入桌宠的 ZIP；
- 提供 macOS 和 Windows 最新桌宠下载入口；
- 通过 GitHub Pages 独立构建和发布。

首屏只加载当前动画，其他角色先显示首帧，接近视口时再加载动画，离开视口后暂停。这让像素动画图鉴在保留表现力的同时，避免一次性解码全部大图。

## 二、两个项目如何协作

当前数据链是单向的：

```text
desktop-pet-mvp/pets/<pet-id>/
        │
        │  desktop-pet-site/scripts/prepare-assets.mjs
        ▼
站点待机预览 + 首帧海报 + 可导入 ZIP + pets.generated.ts
        │
        ▼
Vite 静态构建与 GitHub Pages
```

桌宠的 `pet.json` 与 `spritesheet.webp` 是角色资源真相。站点不维护第二套手写角色清单，而是在需要刷新资源时扫描桌宠仓库，生成：

- 裁剪后的待机动画；
- 轻量首帧海报；
- 保留完整 manifest 和图集的角色 ZIP；
- 供 React 页面读取的类型化数据；
- 从桌宠 `release/` 读取的本地发布元数据。

生产站点的普通 `npm run build` 只读取已经提交的生成资源，因此 GitHub Pages 不依赖相邻仓库。只有角色资源变化时，才在两个仓库相邻的本地工作区运行 `npm run build:refresh-assets`。

桌宠安装包默认使用公开 GitHub Release URL，而不是把大体积安装包提交到站点仓库。角色包属于站点内容，应用安装包属于桌宠发布流程，这两个分发层必须分开。

## 三、关键架构决策

### 1. 桌宠窗口和控制窗口拆分

透明桌宠窗口适合逐像素命中、拖拽和动画，不适合承载复杂表单。把 picker 放进独立普通窗口后，窗口几何、焦点、透明合成和控制 UI 不再互相污染。

这项决策后来继续收缩为 picker-only：控制窗口不再承担通用 settings。结果是窗口契约更容易自动测试，也减少了“打开面板导致桌宠变形、出屏或变成不透明矩形”一类回归。

### 2. 内置资源和用户资源统一

仓库 `pets/` 只作为发布种子；首次运行后，应用只读取 Electron `userData/pets/`。用户添加、改名或删除角色都发生在同一个可写目录中。

发布包中的种子通过 `extraResources` 放到 `resources/pets-seed/`，而不是重复塞进 `app.asar`。首次初始化优先移动，必要时回退为复制，并用一次性标记保证用户删除的内置角色不会在下次启动时自动复活。

### 3. 站点消费 manifest，而不是复制业务逻辑

站点只关心展示所需字段和静态文件，不读取桌宠运行时状态，也不复刻 Electron 的宠物库、选择状态或窗口行为。这让站点可以独立托管，也避免两个前端同时成为角色数据真相。

### 4. 生成资源提交，安装包不提交

站点必须能在没有桌宠兄弟目录的 CI 环境完成构建，所以预览图、角色 ZIP 和生成数据进入站点仓库。桌宠 DMG、Windows ZIP、`release/`、日志和本地配置则始终是发布或运行产物，不进入源码仓库。

## 四、最有价值的工程经验

### 先定义事实源，再谈同步

跨项目最容易出现的问题是“桌宠已经更新，站点仍展示旧角色或旧台词”。解决办法不是人工记得改两次，而是明确生产者和消费者：桌宠 manifest 是源，站点脚本是同步桥，生成结果由构建检查验证。

当角色数量、名称、分类、图集或 manifest 字段变化时，应默认检查两个仓库；当只修改 Electron 窗口行为时，则不应触碰站点。

### 透明窗口问题必须在真实 Electron 中证明

浏览器中的 React 测试无法证明透明像素穿透、置顶、主进程窗口坐标、DPI 缩放或打包后 preload 正常。有效的验证分为三层：

1. 纯函数测试覆盖状态机、几何、manifest 和持久化；
2. Electron smoke 覆盖真实窗口、IPC、选宠和重启恢复；
3. 发布前人工检查透明穿透、拖拽手感和平台窗口外观。

“进程能启动”不等于桌宠可见，“构建成功”也不等于打包资源完整。

### Windows 拖拽只能有一个坐标真相

把 renderer 的 `screenX/screenY` 与主进程坐标混用，会在 Windows DPI 缩放下产生累计漂移。当前方案由主进程的 `screen.getCursorScreenPoint()` 统一提供位置，renderer 只负责判断拖拽阈值、方向和动画。

可复用原则是：涉及原生窗口位置时，坐标系必须集中管理，不能让多个层各自推算后再叠加。

### 打包验证要检查成品，而不只检查源码

项目曾出现源码、开发态都正常，但 Windows 包首次启动不可见、资源没有解包或下载链接指向错误产物的问题。因此发布门禁必须读取最终成品，检查：

- `app.asar` 是否包含必要入口且没有重复宠物资源；
- macOS/Windows 的 `pets-seed` 是否与当前 25 个角色一致；
- Windows ZIP 是否包含完整应用目录，而不是孤立 `.exe`；
- 站点下载文案、文件类型和 GitHub Release 资产是否一致。

### 性能优化应围绕真实资源成本

每个完整图集为 `1536 × 1872`，同时加载 25 个动画的成本远高于普通图片列表。站点通过裁剪待机行、生成首帧、视口懒加载和离屏暂停解决；桌宠 picker 则限制同时预览的 atlas 数量。

这种优化比单纯压缩 JavaScript 更有效，因为瓶颈是图片下载、解码和持续动画，而不是组件数量。

### 删除功能也是架构工作

早期工作日志中出现过设置面板、提醒、外部 API、复杂导入管理和主动行为。真正稳定来自把这些能力连同 IPC、持久化字段、测试、菜单入口和文档一起删除，而不是只隐藏 UI。

每次收缩都应同步清理契约和历史说明，否则旧文档会让后续维护者把已放弃的路线误当待办恢复。

## 五、曾经踩过的坑

| 问题 | 根因 | 最终做法 |
| --- | --- | --- |
| 打开控制面板影响桌宠大小或位置 | 控制 UI 与透明桌宠共用窗口边界 | 拆分 `PetWindow` / `ControlWindow`，用 smoke 固定 bounds 契约 |
| 透明空白区域抢占鼠标 | 用整张动画或矩形范围判断命中 | renderer 按当前帧 alpha 命中，窗口外由主进程复位穿透 |
| Windows 拖拽漂移 | renderer 与主进程混用不同坐标系 | 主进程统一读取屏幕光标坐标 |
| 开发态正常、发布包缺角色 | 只检查源码和 build，没有检查成品 | `release:gate` 后运行 `package:verify` 比对真实包内容 |
| 用户删除内置角色后又被恢复 | 每次启动都把内置资源当默认值复制 | 一次性种子迁移，运行时只读统一用户目录 |
| 站点一次加载所有动态图 | 每张卡直接使用完整图集 | 生成待机行与首帧，接近视口再加载并在离屏暂停 |
| 桌宠内容更新但站点仍旧 | 两边手工维护或忘记刷新生成资源 | 桌宠 manifest 单一事实源，站点脚本生成消费者资源 |
| 下载页与实际 Release 不一致 | 文件名、安装器/便携包策略多次变化 | 下载链接指向 latest release，并在发布时同步核对资产类型 |

## 六、当前验证与发布路径

桌宠日常检查：

```sh
cd desktop-pet-mvp
npm run pet:check
npm run preflight
npm run smoke:electron
```

生成桌宠发布包：

```sh
npm run release:gate
```

站点角色资源变化后的检查：

```sh
cd ../desktop-pet-site
npm run build:refresh-assets
npm run test:performance
```

站点普通代码变化：

```sh
npm run build
npm run test:performance
```

推荐顺序是先完成并验证桌宠资源，再刷新站点生成物；两个仓库分别审查和提交。不要从父目录一次性提交跨仓库内容。

## 七、下一阶段建议

### P0：保持发布真相一致

- 每次发版后验证 GitHub Release 的 macOS DMG 和 Windows ZIP 可下载、可解压、文件名与站点文案一致。
- 将真实桌面人工 smoke 结果记录到发布说明，不用“自动测试通过”代替平台体验验收。

### P1：降低跨仓库同步遗漏

- 给站点增加生成资源陈旧检查：比较桌宠 manifest 摘要与 `pets.generated.ts` 中记录的摘要。
- 在发布清单中固定加入“角色数量、ZIP 数量、预览数量一致”的检查。

### P2：改善资源体积与首开体验

- 继续观察站点首屏 LCP、图片解码和移动端内存，而不是盲目增加动效。
- 如果 25 个离线角色继续增长，再评估种子包分层或可选下载；当前规模下优先保持离线可用和流程简单。

### 暂不优先

- 不恢复复杂 settings、提醒系统或后台 agent 联动；
- 不让站点读取桌宠本地运行状态；
- 不把安装包提交进站点源码；
- 不在两个仓库之间建立隐式自动写入或运行时耦合。

## 八、交接时应记住的原则

1. 运行代码、`package.json`、manifest 和成品验证高于历史计划。
2. 桌宠负责“能运行”，站点负责“能看见、能下载”，两者通过静态资源契约连接。
3. 跨项目改动先判断是否真的影响消费者，再决定是否同步。
4. Electron 的平台行为必须用真实 Electron 或成品证明。
5. 发布完成的定义是源码、构建、安装包、下载入口和人工体验同时一致。
